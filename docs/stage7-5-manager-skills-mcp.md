## 1. Manager (7.5a)

- Вход — **план**: крупная задача и репозиторий. Источник — узел AI Task дерева с пометкой «через менеджера» или API (`POST /exec/plans`). Кнопки в приложении — вместе с канбаном (7.6).
- Сервер ставит хосту работу нового вида `plan`. Manager — Claude **Haiku 5.5** в контейнере, worktree integration смонтирован **только для чтения**, чтобы декомпозиция опиралась на настоящий код.
- Ответ — строгий JSON: список задач (заголовок, текст, `depends_on`, `required_capabilities`, `execution_env`, `review_level`, `touches_ui`, `required_skills`, `mcp_profile`) и короткое обоснование.
- **Менеджер предлагает, оркестратор проверяет и применяет** (ТЗ п. 10.1):
  - граф без циклов, не больше 12 задач;
  - возможности и окружения существуют у хостов;
  - скиллы и MCP-профили есть в реестрах и разрешены для проекта;
  - тексты задач непустые и ограничены по длине.
  - Нарушение → план отклоняется с причиной, Manager получает одну повторную попытку.
- Режимы: в `manual` план ждёт вашего «Утвердить план», в `semi_auto` и `night` задачи создаются сразу. Задачи плана связаны зависимостями: следующая начинается, только когда предыдущая в `DONE`. Это уже работает с 7.2–7.3.

## 2. Скиллы (7.5a)

- **Реестр** — каталог в репозитории `aicrew/skills/<имя>/SKILL.md` с метаданными в заголовке: имя, когда применять, роли, проекты, версия. Версия фиксируется хэшем содержимого.
- Manager выбирает `required_skills[]` по описаниям. Оркестратор пропускает только скиллы из каталога и не запрещённые для проекта. Принудительная привязка и запрет — в настройках репозитория (ТЗ п. 10.2).
- При запуске выбранные скиллы монтируются в контейнер исполнителя **только для чтения** (`~/.claude/skills`), Claude Code подхватывает их сам. Подключение пишется в факты попытки (имя и хэш).
- Скилл — недоверенный контент уровня кода: новые скиллы и правки попадают в каталог только через коммит, который вы одобряете.
- Первый набор (пишу я, вы утверждаете): `flutter-widget-tests`, `dart-clean-code`, `go-backend`, `prompttree-conventions`.

## 3. MCP-реестр (7.5a)

- **Реестр** — `aicrew/mcp/registry.yaml`: сервер, команда запуска, инструменты, scopes (папки, сеть), способ выдачи секретов, логирование вызовов.
- **MCP-профиль задачи** — набор серверов из реестра. Агент получает конфиг только выбранных серверов (`--mcp-config`), больше ничего (ТЗ п. 11).
- Базовые профили:
  - `default` — без MCP: файлы worktree и так доступны встроенными инструментами;
  - `web` — чтение веб-страниц и документации через Jina Reader.
- Вызовы MCP пишутся в факты попытки (инструмент, аргументы без секретов).

## 4. Локальные модели (7.5b)

- **Junior** — Qwen 2.5 Coder (7B, около 5 ГБ) через Ollama. Рутина: тесты, миграции, выжимки документации, `handoff`. Вызывает aicrew-host, модель получает только текст.
- **Vision QA** — Qwen-VL по скриншотам приложения из контейнера с виртуальным экраном, только для задач с `touches_ui` (ТЗ п. 9.4, решение 7.1 п. 3).
- На 8 ГБ видеопамяти модели загружаются по очереди, одновременно не больше одной (решение 7.1 п. 4).

## 5. Roblox (7.5b)

- Окружение `windows_user`: задачи выполняются от пользователя `ai_worker` (без прав администратора и без доступа к вашим папкам), worktree — в его профиле.
- MCP — **встроенный сервер Roblox Studio** (Assistant → Manage MCP Servers → Enable Studio as MCP server). Сторонние серверы не нужны.
- Профиль проверки Roblox: линтер Luau (`selene`) и анализатор (`luau-analyze`), запуск в Studio через MCP (`start_stop_play`, `run_script_in_play_mode`), Vision QA по скриншотам Studio. Скиллы по Luau и Roblox.

## 6. Что будет сделано и проверено (7.5a)

- Сервер: планы (`exec.plans`), работа вида `plan`, проверка плана, «Утвердить план», связь задач плана; `required_skills`, `mcp_profile`, `touches_ui` на задаче.
- Хост: Manager, монтирование скиллов, `--mcp-config` из реестра, факты (скиллы, MCP).
- Тесты: проверка плана (цикл, лишняя возможность, неизвестный скилл, слишком много задач, «вредный» ответ модели), выбор скиллов, MCP-scopes, ручной и полуавтоматический режим плана.
- Прогон на полигоне: одна крупная задача → план из 3–5 задач → выполнение по зависимостям.

## 8. Как сделано

**7.5a.**
- Сервер: `exec.plans` (`QUEUED → PLANNING → AWAITING_APPROVAL → APPROVED`, или `FAILED` / `REJECTED`). Хосту выдаётся работа вида `plan`; у плана свой lease на 15 минут и не больше 2 попыток.
- Проверка плана: граф без циклов, от 1 до 12 задач, только возможности, окружения, исполнители, скиллы и MCP-профили, которые хост прислал при регистрации, и политика скиллов репозитория (`PUT /exec/repositories/{id}/skill-policy`).
- Manager — `internal/manager`. Проверяет план на месте; если план не проходит, Manager получает одну повторную попытку с ошибкой.
- Скиллы — `aicrew/skills`. Монтируются в `~/.claude/skills` только для чтения, имя и хэш пишутся в факты попытки.
- MCP — `aicrew/mcp/registry.yaml`, флаги `--mcp-config` и `--strict-mcp-config`.
- Junior — тот же Claude Code, но с `ANTHROPIC_BASE_URL` на Ollama (Anthropic-совместимый API). Задачи `junior` выдаются только хостам, где модель скачана.

**7.5b.**
- Vision QA — `internal/vision`, образ `aicrew/images/vision`: веб-сборка, снимки телефона и десктопа, Qwen-VL, `keep_alive: 0`.
- Модели Ollama лежат в `D:\Ollama\models` (настройка «Model location» приложения Ollama плюс переменная `OLLAMA_MODELS`).
- Окружение `windows_user` — `internal/runas`:
  - запуск через `CreateProcessWithLogonW` от `ai_worker`;
  - Job-объект: таймаут или отмена убивают всё дерево процессов;
  - окружение собирается без путей профиля владельца, токен передаётся в окружении, а не в командной строке;
  - запускаются только перечисленные программы.
- Исполнитель — `claude.exe` без контейнера; скиллы подключаются через `CLAUDE_CONFIG_DIR`. Проверки — `verify.Native` (шаблон `roblox`: `stylua`, `selene`).
- Настройка — `aicrew/setup/windows-ai-worker.ps1` (запускает владелец от имени администратора) и `aicrew-host set-worker -roblox`.
