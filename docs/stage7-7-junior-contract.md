# Этап 7.7. Junior по контракту

Решение владельца — 13.10.2026: «Claude говорит, какие нужны функции и файлы, qwen делает по одной, Claude соединяет».
Junior больше нельзя выбрать задачей напрямую.

## Почему

- **Прямой Junior (12.10.2026) не справился.** Живая задача «перетаскивание задач» на qwen3:8b 60 ходов подряд читала один файл.
  - qwen3-coder:30b задачу сделал, но на ПК с 32 ГБ памяти вместе с Docker довёл до синего экрана.
  - Маленькой модели не хватает длинной цепочки решений.
  - Узкое задание с точной целью ей по силам.
- **Экономия только там, где есть механическая работа.** Claude всё равно читает код, пишет задание и собирает результат.
  - На маленьких или сложных задачах выигрыша нет.
  - Поэтому Manager отдаёт Junior работу, только когда это реально её снимает.

## Как устроено

Каждая работа Junior — «бутерброд» из трёх задач плана Manager'а:

1. **Контракт — Claude.**
   - Пишет интерфейсы и заглушки.
   - Пишет тесты, которые задают каждую часть Junior.
   - Помечает эти тесты пропущенными с причиной `aicrew-contract` (Dart: `skip: 'aicrew-contract'`; Go: `t.Skip("aicrew-contract")`).
   - Проверки проходят, потому что тесты пропущены.
2. **Часть — Junior.** Задача зависит от задачи контракта и несёт `contract: {files, tests}`.
   - Перед стартом служба сама снимает метку пропуска в тестах контракта. Если метки нет — `contract_missing`.
   - Junior только пишет код в файлах `files`, тесты ему трогать нельзя. Метку раньше снимал он сам; замер 18.10.2026 показал, что маленькие модели её не замечают.
   - После работы служба проверяет:
     - изменены только файлы из `files` — иначе `contract_broken`; файлы, которые пересоздают сами инструменты Flutter (`generated_plugin_registrant.*`, `generated_plugins.cmake`), не в счёт;
     - тесты ровно такие, какими их выдала служба — иначе `contract_broken`;
     - дальше обычные проверки: анализатор и все тесты, включая ожившие.
3. **Сборка — Claude.** Зависит от задач Junior: подключает их работу к фиче и вычитывает.

## Правила

Их проверяют Manager на ПК и сервер при приёме плана.

| Правило | Где ещё |
|---|---|
| У задачи `junior` есть контракт: 1–12 путей, относительные, без `..`. | — |
| Перед задачей `junior` идёт задача `claude`, после неё — тоже `claude`. | — |
| Junior не делает того, что видит пользователь (`touches_ui`). | Экраны, тексты интерфейса и дизайн — только Claude с согласованием владельца. |
| `POST /exec/tasks` с `executor: junior` отклоняется: `junior_only_in_plan`. | Окно «Отправить в AiCrew…» выбора исполнителя не показывает. |

## Как сравнить расход

- Служба пишет в журнал по каждой попытке строку `agent usage`: исполнитель, ходы, токены, стоимость, секунды.
- Manager пишет строку `manager finished`.
- Сравнение: одну и ту же фичу отправить «одной задачей» и «через Manager», затем сложить стоимость задач Claude.

## Локальная модель на этом ПК

- qwen3:8b, окно 16k, целиком в видеокарте 8 ГБ.
- Защита памяти: служба не запускает модель, если её остаток не влезает в свободную оперативную память. Видеопамять при этом учитывается.
- После попытки служба сразу выгружает модель.
- Ответ модели ограничен 4096 токенами.
- Одинаковые вызовы подряд: на третьем служба напоминает, на пятом завершает попытку (`looping`).
- «Готово» без единой правки не принимается: модели дважды отвечают «ты ещё ничего не изменил».
- Если правка не нашла фрагмент, модель получает текущий текст файла (до 6 КБ), а не просьбу перечитать его.
