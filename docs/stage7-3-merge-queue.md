# Этап 7.3 — очередь слияния, integration-ветка, откат

Статус: **на согласовании**.

Цель этапа — первый полезный результат AiCrew (документ 7.1, раздел 6): «AI Task из дерева → Claude Code в песочнице → тесты → слияние в integration-ветку». Сейчас успешная задача останавливается в `MERGEABLE`, и сливать её приходится вручную. Первую задачу полигона я слил так 08.10.2026.

## 1. Ветки

| Ветка | Кто пишет | Зачем |
|---|---|---|
| `main` | только Максим | рабочая версия; AiCrew в неё не пишет никогда |
| `aicrew/integration` | только очередь слияния | сюда попадают проверенные результаты задач |
| `aicrew/task-<id>` | исполнитель задачи | работа одной задачи в своём worktree (есть с 7.2) |

Задача начинается от свежего `aicrew/integration`, а не от `main`. Так следующая задача видит результат предыдущей.

## 2. Очередь слияния (на домашнем ПК, в службе aicrew-host)

Задачи сливаются **строго по одной**:

1. Задача в `MERGEABLE` встаёт в очередь. В режиме `manual` она сначала ждёт вашего «Слить»; в режимах `semi_auto` и `night` встаёт сама.
2. Служба создаёт временный worktree от текущего `aicrew/integration` и делает `git merge --no-ff aicrew/task-<id>`. У каждой задачи получается один коммит слияния, поэтому её легко откатить целиком.
3. **Конфликт.** Задача возвращается в работу (`REWORK`) от свежего integration. Исполнитель получает список конфликтных файлов и делает задачу заново поверх чужих изменений. Сам Claude конфликт внутри merge не разрешает: так проще проверить результат.
4. **Проверка результата слияния** (`POST_MERGE_VERIFY`) тем же профилем репозитория. Это ловит случай «A и B по отдельности проходят, вместе ломают».
5. Проверка прошла → `aicrew/integration` переходит на коммит слияния (fast-forward) → `MERGED` → `DONE`, worktree задачи удаляется.
   Проверка упала → integration **не двигается**, задача уходит в `REWORK` с фактами (класс `INTEGRATION_FAILURE`, вывод упавшего шага).
6. Ветка integration всегда зелёная: в неё попадает только проверенный результат слияния.

## 3. Откат

- Команда «Откатить задачу» делает `git revert -m 1 <коммит слияния>` через ту же очередь, то есть с проверкой после отката. Статус задачи становится `ROLLED_BACK`, в аудит пишется, кто и почему откатил.
- Нельзя откатить задачу, на которую опираются более поздние (`depends_on`), не откатив сначала их. Оркестратор покажет цепочку.

## 4. integration → main

Переносите вы, кнопкой «Перенести в main» или вручную: `git merge --ff-only aicrew/integration`. Перед переносом служба ещё раз прогоняет проверку на integration.

## 5. Что будет сделано и проверено

- Сервер: состояния `MERGE_QUEUED`, `MERGING`, `POST_MERGE_VERIFY`, `MERGED`, `DONE`, `REWORK`, `ROLLED_BACK`; эндпоинты «слить», «откатить», «перенести в main» (последний только записывает разрешение, сам git на ПК); блокировка очереди на один репозиторий.
- aicrew-host: очередь слияния, проверка после слияния, откат, уборка worktree.
- Тесты, в том числе сценарии из 7.1: конфликт слияния; две задачи, которые по отдельности зелёные, а вместе ломают тест; откат с проверкой.
- Прогон на полигоне: ещё 4–9 задач (всего 5–10, решение 7.1 п. 3), среди них нарочно конфликтующие.

## 6. Вопросы

1. **integration → main всегда только вы?** Предлагаю да, на всё время полигона и первых недель на PromptTree.
2. **В режиме `manual` нужно ваше «Слить» перед integration?** Предлагаю да. В `semi_auto` — без него.
3. **Конфликт: сразу переделывать задачу или сначала дать Claude один раз разрешить конфликт?** Предлагаю переделывать: результат проще проверить, а лишняя попытка дешевле, чем незаметно испорченное слияние.
