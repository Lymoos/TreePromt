## 2. Профили проверки (шаг 1)

Встроенные шаблоны; репозиторий выбирает шаблон и при необходимости переопределяет шаги:

- **Flutter:** `flutter pub get` → `dart format --set-exit-if-changed .` → `flutter analyze` → `flutter test --machine` → `flutter build web` (см. вопрос 3).
- **Go:** `gofmt -l .` (провал, если вывод не пустой) → `go vet ./...` → `go test -json ./...` → `go build ./...`.
- **Web (Node):** `npm ci` → `npm run lint` (если есть) → `npm test` → `npm run build`; браузерные тесты — Playwright, если в репозитории есть его конфиг. Для веба отдельный образ `aicrew-agent-web` (Node + Chromium), собирается по требованию.
- Шаги — только argv, без оболочки (`sh -c` запрещён, ТЗ п. 12). Для «вывод должен быть пустым» у шага есть флаг `fail_on_output`.
- **`test_report.json`:** вывод `flutter test --machine` и `go test -json` разбирается кодом в отчёт: сколько тестов, какие упали и с каким сообщением. Это лучшие факты для исправления и для ревьюера.

## 3. Контракт архитектуры (шаг 2)

`architecture.yaml` лежит в корне репозитория и описывает:

```yaml
version: 1
modules:                       # модуль = набор путей
  ui:     { paths: ["lib/ui/**"] }
  domain: { paths: ["lib/domain/**"] }
  data:   { paths: ["lib/data/**"] }
allow:                         # кто от кого может зависеть; остальное запрещено
  ui: [domain]
  data: [domain]
forbidden_imports: ["dart:mirrors", "package:http/http.dart"]   # пакеты, которые нельзя подключать
protected_paths:               # правка требует вашего одобрения (ТЗ п. 13)
  - pubspec.yaml               # новые зависимости
  - "**/migrations/**"         # схема БД
  - architecture.yaml          # сам контракт
readonly_paths: [".github/**"] # агенту трогать нельзя вообще
```

- Валидатор на Go разбирает импорты в изменённых файлах (Dart: `import`/`export`, Go: `import`), сопоставляет файлы модулям и проверяет связи. Это код, а не модель (ТЗ п. 9.2).
- **Нарушение** (запрещённая связь, запрещённый пакет, правка `readonly_paths`) → `FAILED`, класс `QA_REJECT`, `rejection_type: contract`, со списком нарушений. Задача переделывается.
- **Правка `protected_paths`** — не ошибка, а изменение, которое требует одобрения: задача проходит проверки, но в очередь слияния сама не встаёт даже в `semi_auto` и `night`. Она ждёт вашего «Слить» с пометкой, что именно требует одобрения (вопрос 2).
- Нет `architecture.yaml` — шаг пропускается с пометкой в фактах. Первые контракты (полигон, PromptTree) пишу я, вы утверждаете. Агент Architect, который предлагает изменения контракта, — в 7.5.

## 4. Logic QA (шаг 3)

- aicrew-host отправляет на сервер **факты**: текст задачи, `git diff` (с лимитом размера), `diff --stat`, `test_report.json`, итог контракта, список файлов. Итог работы исполнителя — только как дополнительный контекст (ТЗ п. 9).
- Сервер вызывает Gemini Flash со строгим JSON-контрактом ответа: `verdict` (approve | reject), `rejection_type` (code_bug | environment | qa_error | outdated_contract), `issues[]` (файл, строка, серьёзность, текст), `summary`. Ответ проверяет валидатор, как в этапе 6. Невалидный ответ → повтор, затем `ENVIRONMENT_FAILURE`.
- Статус двигает сервер, а не модель: approve → `MERGEABLE`; reject → `FAILED`, класс `QA_REJECT`, замечания уходят в следующую попытку.
- Diff и код — недоверенные данные: в промпте ревьюера они лежат в ограниченном блоке с указанием игнорировать инструкции внутри (prompt injection, ТЗ п. 12).
- Бюджет: отдельный дневной лимит вызовов Logic QA и таймаут `review_runtime`. Отказы с `rejection_type` копятся в статистике — это основа QA Kill Switch в 7.6.

## 5. Tech Lead (шаг 4)

Для задач с пометкой `review: tech_lead`: Claude Code (Sonnet) в контейнере с worktree, **только чтение** (`--allowedTools Read,Grep,Glob`), получает те же факты и отвечает тем же JSON. Пометку ставите вы при создании задачи. С 7.5 её ставит Manager.

## 6. Что будет сделано и проверено

- Профили Flutter / Go / Web, разбор отчётов тестов, `fail_on_output`, образ `aicrew-agent-web`.
- Валидатор `architecture.yaml` и контракт для полигона.
- Logic QA на сервере (`POST /exec/tasks/{id}/review`), JSON-контракт и валидатор, лимиты; Tech Lead на хосте.
- Тесты: красные тесты → `TEST_FAILURE` с именами тестов; нарушение контракта → `QA_REJECT`; правка `protected_paths` в `semi_auto` не сливается сама; ревьюер отклоняет → замечания доходят до следующей попытки; невалидный и «вредный» ответ модели; prompt injection в diff.
- Прогон на полигоне: несколько задач, среди них нарочно нарушающие контракт и с ошибкой, которую ловит только ревью.
