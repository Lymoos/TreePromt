# Этап 7.6 — безопасность, Incident Kill Switch, аудит, ApprovalRequest, канбан

Статус: **в работе** (Максим, 12.10.2026: «7.6 делай»). Интерфейс канбана — только после утверждения макета (правило: решения по интерфейсу сначала согласуются).

Последний этап AiCrew (документ 7.1, раздел 6): система должна быть безопасной без присмотра, особенно ночью, и оставлять полный след.

## 1. Сканер секретов (ТЗ п. 12)

Проверяет код хоста в трёх местах:
1. **Перед автокоммитом** — все изменения исполнителя, включая новые файлы.
2. **Перед отправкой текста модели** — задача, факты и diff для ревьюера, запрос Manager'у.
3. **Перед сохранением фактов и логов** — итог агента, вывод команд, причины ошибок.

Что ищется:
- **Точные значения секретов этого хоста:** токен Claude, пароль `ai_worker`, refresh-токен сервера. Самая надёжная проверка.
- **Известные форматы:** ключи Anthropic, OpenAI, Google (`AIza…`), GitHub (`ghp_`, `github_pat_`), Slack, AWS (`AKIA…`), JWT, блоки `PRIVATE KEY`, строки подключения с паролем.
- **Присваивания `password=`, `secret=`, `token=`** с длинным значением высокой энтропии. Явные заглушки вроде `example` и `changeme` пропускаются.

Если секрет найден:
- **В изменениях исполнителя** — коммита нет, задача сразу уходит к человеку (класс `SECRET_LEAK`, без повторов), worktree удаляется, в ночную смену срабатывает Kill Switch (раздел 2).
- **В тексте для модели или в логах** — значение заменяется на `[REDACTED:тип]`. Сервер повторяет замену у себя, вторым рубежом.

## 2. Incident Kill Switch (ТЗ п. 12)

Инцидент открывается в трёх случаях:
- **`integration_red`** — integration была зелёной, а 3 слияния подряд не прошли проверку после слияния (`INTEGRATION_FAILURE`) или упал перенос в `main`;
- **`secret_leak`** — сканер нашёл секрет в изменениях исполнителя;
- **`qa_spike`** — QA Kill Switch: из последних 10 ревью больше 7 отказов. Это значит, что ревьюер сломался, а не код.

Что происходит при инциденте:
- репозиторий на паузе: новые задачи не берутся, слияния не идут;
- ночная смена (`night`) по всем репозиториям останавливается;
- приходит уведомление в приложение через realtime-канал (пуш-уведомления — вместе с канбаном).

Снимает паузу только человек: «Возобновить» с комментарием. Есть и ручной рубильник: «Остановить всё» и «Остановить репозиторий».

## 3. Аудит (ТЗ п. 14)

- `exec.audit` — **только добавление**: изменение и удаление записей запрещены триггером базы. Что пишется:
  - каждая команда хоста: программа, argv после сканера, каталог, exit-код, длительность;
  - каждый вызов модели: роль, провайдер и модель, хэш промпта, расход;
  - подключённые скиллы (имя и хэш) и MCP-профиль;
  - смены статусов (они уже есть в `task_events`).
- **Снимки промптов** без секретов хранятся по хэшу в `exec.prompt_snapshots`: по хэшу из аудита можно увидеть, что именно получила модель.
- Хост отправляет записи пачками. Если сеть пропала, они ждут в очереди на диске и потом досылаются.

## 4. ApprovalRequest (ТЗ п. 13)

Запрос на решение человека создаётся:
- при `MERGEABLE` в ручном режиме;
- при правке `protected_paths`;
- для плана Manager'а в ручном режиме;
- при инциденте.

Поля: тип, задача или план, содержание (diff, план, причина), статус, кто решил, комментарий, срок.

Варианты решения:
- **принять**;
- **отклонить с комментарием**: задача уходит на новую попытку поверх свежего integration, комментарий доходит до исполнителя как главный урок. Отклонённый план отправляется Manager'у заново вместе с комментарием;
- **принять частично** (для плана): выбранные задачи создаются, остальные отбрасываются.

Срок ожидания задаётся. Ночью запросы не блокируют независимые ветки графа задач: так уже устроены зависимости. Нынешние «Слить» и «Утвердить план» становятся ответами на запрос, старые API продолжают работать.

## 5. Канбан в приложении

Колонки по статусам: очередь, в работе, проверка, ждёт решения, слито, ошибки. Карточки задач и планов, запросы на решение, инциденты, аватары исполнителей из реестра хостов и воркеров (ТЗ п. 8.1). **Сначала макет на утверждение**, потом код в `shared/`.

## 6. Что будет проверено

- Сканер: каждый формат; точные значения хоста; заглушки не срабатывают; секрет в новом файле останавливает задачу без коммита; редактирование промптов и логов.
- Kill Switch: три провала integration подряд → пауза; пауза не даёт брать задачи и сливать; ночь останавливается; ручное «Возобновить».
- Аудит: записи нельзя изменить и удалить (триггер); снимок промпта без секрета.
- ApprovalRequest: отклонение с комментарием → новая попытка с уроком; частичное принятие плана; срок.
- Command Policy (ТЗ п. 16): обход через `sh -c` невозможен — шаги проверки только argv, `runas` пускает только перечисленные программы.
